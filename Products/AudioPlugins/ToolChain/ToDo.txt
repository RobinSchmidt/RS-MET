Bugs

We give the priorities from 1 to 5 with meanings:

[1]  Minor annoyance: cosmetic GUI issues, mildly inconvenient behavior
[2]  Major annoyance: things like unresponsive GUI or false GUI feedback
[3]  Minor feature not working (like zoom in a plot, highlighting of GUI elements)
[4]  Major feature not working (like setting an important DSP parameter)
[5]  Showstoppers: crashes, false state recalls, filter instability explosions, wrong signals, 
     Nans, infinities, ...

In addition to the priorities 1-5, we also use the following tags:

[Q]  Questionable behavior which might in fact be correct/intended/expected and therefore not 
     strictly a bug but might be perceived as such. Maybe it's a design mistake.
[F]  Fixed, not verified
[V]  Fixed and verified

For fixing a bug, the preferable workflow is to first write a unit test in the TestAppJURA project 
that triggers and checks the buggy behavior programmatically and only *then* fixing it. This way, 
we build up our suite of unit tests along the way.

Code Quality

- Use an enum class for listing the different effect algos in rosic::Quadrifex::effectAlgorithms.
  We should generally use enum classes for such options.

- We should not use User/AppData/Roaming/RS-MET as the default location for storing data. Instead,
  we should do it like Surge XT and use Documents/RS-MET. Maybe we can use 
  JUCE::File::getSpecialLocation? Look into the Surge codebase for how they do it.

- In some AudioModule subclasses (for example EqualizerAudioModule), we have a pointer to an 
  underlying DSP core object which in some situations may be an owned pointer (i.e. created via 
  new in the constructor and deleted in the destuctor) and in some other situations, it may be a 
  pointer to an existing DSP core object around which we just "wrap" the AudioModule for 
  controlling it without also managing its lifetime. The AudioModule subclass maintains a boolean 
  "..IsOwned" flag to distinguish between the two cases. That strategy appears again and again and
  should therefore be factored out into a sort of smart-pointer class that can be owning or 
  non-owning. It should hold the pointer to the object (so it should be templatized on the object 
  type T) and have a bool "isOwned" flag. When the constructor of this smart-pointer is called with 
  a nullptr parameter, it should create a new instance of T and set isOwned to true. If the 
  constructor is called with an existing pointee, it should just set the pointer member to it and 
  set isOwned to false. The destructor should check the isOwned flag and call delete on the object, 
  iff isOwned is true. The constructor of e.g. EqualizerAudioModule should pass the pointer 
  argument via its constructor list to the smart pointer class. The smart pointer class could also
  provide functionality like setObject(T* newPointee, bool isOwned = false) to set the object later
  but typically, the pointee should be passed to the constructor and iff a nullptr is passed to the 
  constructor, the constructor should itself create a new object and consider it as owned (and 
  therefore delete it in the destructor). This idiom should be used in all subclasses of 
  jura::AudioModule that hold a pointer to an owned or non-owned DSP object. Maybe the class could 
  be named rsOwnedOrNonOwnedPointer<T> or rsMaybeOwnedPointer<T> and should probably be part of
  the jura_framework module. Maybe it could also be in rosic. Maybe the smart-pointer member 
  variables in the AudioModule should be consistently called something like "dspCore" to establish
  an idiomatic way to do this.

- In jura, also use the "rs" prefix consistently like in rapt and rosic. Some widget classes 
  currently use an "R" prefix (RSlider, RButton,  etc.). This should be replaced by "rs" as well. 
  Rename some things in jura:
    ColourSchemeComponent::updateWidgetsAccordingToState()  ->  updateWidgetsFromState()
    ColourSchemeComponent  ->   ColorSchemeComponent

  explain the ways it's done in JUCE and other frameworks (if they have such a feature) as well as 
  in popular open source instruments such as Surge, ShortCircuit, Pure Data, etc. I want to figure 
  out a general design pattern that can be used to turn any monophonic DSP algorithm into a
  polyphonic one with minimum coding effort - but it should also be efficient in the sense that 
  data that can be shared between the voices is not duplicated. Maybe Copilot Spaces is te right
  way to have such conversations. See:
  https://docs.github.com/en/copilot/how-tos/provide-context/use-copilot-spaces
  https://docs.github.com/en/copilot/how-tos/provide-context/use-copilot-spaces/create-copilot-spaces
  https://docs.github.com/en/copilot/concepts/context/spaces

- Currently, when I integrate a new DSP algorithm into ToolChain for demonstration and 
  experimentation purposes, I tend to define a subclass of jura::AudioModule for it and then make
  it available withing the semi-modular framework of ToolChain and then play around with it. But
  this habit will lead to an unreasonable proliferation of modules in ToolChain. A better approach
  may be to integrate the new DSP algorithm as a module in the node based modular synthesizer 
  Liberty. I think, there, it may even automatically become polyphonic. Maybe try it with the 
  pitch dithered oscillator.
