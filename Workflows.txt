Running tests and experiments:

Open: TestsRosicAndRapt.sln
in:   RS-MET\Tests\TestsRosicAndRapt\Builds\VisualStudio2019

and then in Main.cpp uncomment one or more lines for the experiment(s), you want to run (and 
comment any experiment that you don't want to run but is currently uncommented). Then compile and 
run, preferably in debug mode, unless you want to do performance tests. The unit- and performance 
tests will produce console output for the results. The experiments will produce wave-files in the 
project directory and/or use GNUPlotCPP to open a window with plots for the results (if you have 
GNUPlot installed and GNUPlotter correctly set up - the file is in rapt/Basics). Navigate to the 
code for a particular test by right-clicking on the function-call and using "Go To 
Definition/Declaration". If so desired, new tests and experiments can be added easily by just 
following the apparent pattern.

Note that on the Mac, the created files end up in the user's home folder ("rob" on my machine) 
when TestsRosicAndRapt is executed directly (e.g. with double-click from Finder). On the other 
hand, when executed from Xcode (e.g. via the "Play" button), they end up in the in build/Debug.

Writing APE Scripts:

Open the JUCE PluginHost, for example, using AudioPluginHost.exe from 

  RS-MET\Products\Applications\AudioPluginHost\Builds\VisualStudio2017\x64\Release\App\

after you have built the project. Then plug in an APE instance and load the script with which you
want to work (or create a new one). My scripts are located in:

  RS-MET\Misc\APE Scripts

Wire up APE as desired. For filters and effects, I like to place a ToolChain instance in front of 
APE that runs a simple oscillator (for example using Straightliner) and place another instance of
ToolChain after APE for running some sort of analysis (oscilloscope, spectrum analyzer, etc.). 
Obviously, you may use different plugins for creating source signals and analyzing the output. For 
editing the script, it may be convenient to use an external text editor such as Notepad++, 
Visual Studio Code, Sublime, etc. For editing library code (rapt/rosic) in such a session, it may 
be a good idea to do that in Visual Studio, running the TestsRosicAndRapt.sln solution in parallel
and check occasionally if everything still compiles after the edits. Maybe also run occasionally 
the relevant unit tests (i.e. uncomment runUnitTestsRapt, etc. in Main.cpp). It's also useful to 
have Visual Studio open for navigating the library. When editing the script in an external editor,
we need to reload the script in APE (using File -> Open recent). APE does not automatically 
recognize external changes.

Adding a module to ToolChain:

Step 1: 
Implement the module as subclass of jura::AudioModule or a suitable subclass thereof (like 
AudioModuleWithMidiIn). (1a) Create the class. (1b) Add the required boilerplate code to the class
for the glue and plumbing.

Step 2:
Add an entry for the new module in ToolChain::populateModuleFactory() in a suitable category.

Done! That's all there is to it!

Managing the repository (plan - not yet fully realized):

There should be 4 branches with varying levels of maturity vs preliminarity

release:
-Should contain the version of the code from the latest official release.
-Should build on all target platforms in Debug and Release mode without compiler warnings.
-Code should be thoroughly tested. All unit tests must pass. All performance tests must produce 
 reasonably good results.

master:
-Should build on all target platforms in Debug and Release mode.
-Should build after re-generating the IDE project files from Projucer and should do so with a 
 reasonable amount of warnings without tweaking the warning level in the IDE. What is "reasonable"?
 I don't know. Try to get rid of as many as possible.
-Should be reasonably tested and debugged.

develop:
-Should build on Windows in Visual Studio and on macOS in XCode in Debug and Release mode.

work:
-Should build on Windows in Visual Studio in Debug mode (the primary dev environment).

The other repos (RS-MET-Research, RS-MET-Tests, ...) should use the same branch structure and we 
should avoid that, say, a master branch of the Research repo depends on code in the develop or work
work branch of the main repo.

 -Open the .jucer files in the projects with Projucer and click on File -> Save Project. This will

  To get the project files for the latest version of Visual Studio and XCode, use the Projucer 8. To

  files and the .cpp file to the corresponding #include list in the corresponding (unity build) .cpp

Workflow patterns using AI assistance:

Coding:

- "Create Stub -> Document Functionality -> Generate Code"
  To write a function with the help of Copilot, write a stub for the function and the documentation 
  that explains what the function does (or rather is supposed to do). Then use autocomplete 
  ("Alt" + ".") inside the stub. Copilot can often generate the code from the previously created 
  documentation. Maybe also write a unit test for it to further document its expected behavior (in 
  test driven development (TDD) style: Write the test first and let it fail successfully, then 
  work on the feature until the test passes). Maybe if autocomplete is not enough, prompt Copilot to
  generate the code for the implementation.

- "Glorified Find-and-Replace" or "Natural Language Batch Processor"
  Not yet tried - just and idea that could plausibly work well:
  Use AI as a sort of natural language controlled batch processor to do the same kind of code change
  in a whole bunch of source files (maybe in a whole codebase). It would be like a glorified "find 
  and replace" that can do more complex changes than regular "find and replace" (even with regex) 
  but which are still just tedious and boring grunt work. Things like "Find all "typedef" 
  declarations and replace them by the corresponding "using" declaration.". Well, that change could 
  probably still be done with regex but I really wouldn't want to work out how (maybe ask AI to do 
  the translation! ;-)). Other example: Change all enum entries to use lowerCamelCase and do all the
  required updates of the codebase that uses these entries. Or: Replace all occurrences of 
  "#pragma once" by old school C-style include guards using the format 
  "#ifndef RAPT_FILENAME_INCLUDED #define RAPT_FILENAME_INCLUDED  ...  #endif" where "FILENAME" 
  should be infered from the name of the .h file. Or: prefix all class names in the "jura" namespace
  with "rs" and do all the required updates in client code. Or: "Fix all compiler warnings about 
  unused local variables by commenting their declarations out". Or: "Fix all compiler warnings about
  unused function parameters by commenting their declarations out". Or: "Make this optional function
  parameter mandatory and find all call sites and pass the former default value there". Maybe do the 
  change manually in one place and point the AI to that place to use it as template. Or maybe create
  a "before - after" template/example in the prompt. Maybe a few more examples with some variations 
  that are likely to be encountered.

- More ideas: Use AI to clean up unneeded #includes. It sometimes happens that we include more than 
  we need, for example, when we need some library at one point in time but later get rid of the 
  dependency without even realizing it due to code changes. AI should also be well suited for 
  generating and modifying(!) boilerplate code. Especially the modification of large amounts of 
  existing boilerplate is often a big pile of grunt work which should be automated by AI. Chatting
  with an AI can also be great for brainstorming as in generating and refining ideas, weeding out 
  the bad ideas, etc. For this, I just go to a chatbot and start a conversation by asking a 
  (technical) question with possible follow-up questions. It often makes sense to then save the 
  conversation for later reference. It seems like Claude Sonnet is currently (in 2026) regarded as 
  one of the best models for this purpose when it's about math, algorithms and programming. See:
  https://claude.ai/share/4d6c2630-30d6-4010-94d4-27a7e0225391  for an example
  

Debugging:

- "Describe Bug -> Generate Explanation"
  What sometimes works to find a bug is to go into the code section where the bug might probably be 
  and start writing a comment that explains the bug and then something like: "Maybe the problem 
  is...", "It's likely that ...", .. and then using autocomplete to see what Copilot comes up with.
  It sometimes actually gets it right and correctly explains what is wrong.
  
- "Explain Intent -> Fix Syntax"  
  C++ can have a rather awkward syntax for certain things and I sometimes get it wrong and produce
  compile errors with error messages that leave me totally dumbfounded. In such cases, it often 
  helps to explain Copilot what I'm trying to achieve, what error messages I get and to ask for the
  correct C++ syntax for what I'm trying to do.
  
- Ask AI to look over some segment of code and find suspicious looking things. Can also be used to 
  find wrong formulas in math papers and books
